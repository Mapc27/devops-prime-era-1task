# M5 — вердикт и объяснение (локальная LLM)

`qwen2.5:3b-instruct` Q4 через Ollama. **LLM не принимает решение**: вердикт
считает детерминированное правило, модель отвечает только за текст объяснения.

## Подготовка

```bash
brew install ollama
ollama serve        # в отдельном терминале
ollama pull qwen2.5:3b-instruct
```

## Запуск

```bash
.venv/bin/python m5_llm/make_cases.py
.venv/bin/python m5_llm/verdict.py --index 3
.venv/bin/python m5_llm/benchmark.py \
    --models qwen2.5:7b-instruct qwen2.5:3b-instruct --repeats 3
```

## Результаты

По 16 кейсов трижды — 48 запросов на модель.

| Показатель | qwen2.5-7b | qwen2.5-3b |
|---|---|---|
| валидный JSON | 100% | 100% |
| совпадение вердикта | 81.2% | **100%** |
| текст без дефектов | **100%** | 93.8% |
| генерация | 44.4 ток/с | **83.4 ток/с** |
| память | 4521 МБ | **2055 МБ** |

## Что важно знать

- **Меньшая модель точнее следует правилу, крупная пишет чище.** 7B ошибается
  с вердиктом на одних и тех же трёх кейсах во всех повторах (два смешанных
  и «только текст»), 3B не ошибается ни разу. Зато 3B в 3 ответах из 48
  вставляет в текст для продавца служебные термины (`review`, `allow`).
  Выбрана 3B: дефект текста исправим постобработкой, ошибка смысла — нет.
- `verdict.py` запрашивает объяснение повторно, если вердикт модели разошёлся
  с правилом: текст для продавца не должен описывать не тот вердикт.
- 100% валидного JSON получается не из-за промпта, а потому что в запрос
  передаётся JSON-схема: сервер ограничивает генерацию на этапе выбора токенов.
- Память берётся из `/api/ps`, перед замером модели выгружаются — иначе
  при сравнении двух моделей в памяти висят обе.
