# Техническое задание

## Задача

**Предмодерация объявлений на площадке частных объявлений.** Объявление состоит
из четырёх типов контента: текстовое описание, фотографии, видеообзор, голосовой
комментарий. Ручная модерация не справляется с потоком, нужна автоматическая
предфильтрация.

Каждый модуль относит контент к одной из трёх корзин: `allow` (публиковать),
`review` (модератору), `reject` (отклонить).

### Цена ошибки

Ошибки несимметричны. Ложная блокировка честного объявления дороже пропущенного
нарушения: продавец теряет деньги и уходит, тогда как пропуск ловится жалобами
и постмодерацией.

Отсюда главное требование — **precision(reject) >= 0.95**, а recall
максимизируется уже под ним. Всё неуверенное идёт в `review`, а не в отказ.
Корзина `review` при этом не должна превышать 20% потока, иначе автоматизация
теряет смысл.

### Ограничения

- Модели предобученные, обучение и дообучение не проводятся.
- Всё работает локально, без обращения к внешним API.
- Интерфейс — CLI. Модуль M1 дополнительно оформляется как HTTP-сервис.

## Модули

```
объявление
  ├── текст ──────────► M1  детекция нарушений в тексте
  ├── фото ───────────► M2  соответствие фото заявленной категории
  ├── голосовое ──────► M3  распознавание речи ──► M1
  ├── видео ──────────► M4  проверка наличия заявленного объекта
  └── результаты M1-M4 ► M5  вердикт и формулировка причины (LLM)
```

### M1. Текст

**Вход:** строка до 5000 символов, русский язык. **Выход:** оценка нарушения,
решение, вид нарушения для объяснения продавцу.

**Критерии приёмки:** precision(reject) >= 0.95; доля `review` <= 20%;
латентность p95 < 100 мс на CPU.

**Метрики.** ML: ROC-AUC, PR-AUC, precision/recall по классам, матрица ошибок,
разбивка по видам нарушений. Продуктовые: доля автоматических решений, нагрузка
на модераторов, доля утечки нарушений в публикацию. Инфраструктурные:
латентность p50/p95, пропускная способность, RSS.

**Данные для оценки.** Публичный корпус русских токсичных комментариев
(6000 текстов) и собственный набор объявлений (200 текстов, разбит на подгруппы
по видам нарушений и по видам законных резких формулировок).

Доля нарушений в публичном корпусе выше ожидаемой в потоке объявлений,
а precision зависит от базовой частоты класса, поэтому она пересчитывается
на ожидаемые 5% аналитически.

### M2. Изображение

**Вход:** JPEG/PNG + заявленная категория из справочника. **Выход:**
предсказанная категория, уверенность, флаг соответствия.

**Почему zero-shot:** категорий сотни и они меняются; обучать классификатор под
каждую нельзя. Модель, сопоставляющая изображение с текстовым описанием
категории, переживает добавление новых категорий — достаточно дописать строку
в справочник.

**Критерии приёмки:** top-1 accuracy >= 0.85; recall детекции несоответствия
>= 0.80 при precision >= 0.90; время на изображение < 200 мс.

**Метрики.** ML: top-1/top-3 accuracy, precision/recall детекции несоответствия,
**сравнение с обученным классификатором на тех же классах** — цена
универсальности. Инфраструктурные: время на изображение CPU против GPU,
выигрыш от батчинга, память.

**Данные для оценки.** Публичный датасет изображений с разметкой по классам
(500 изображений). Для измерения детекции подмены каждому изображению
дополнительно приписывается заведомо неверная категория.

### M3. Аудио

**Вход:** аудиофайл до 5 минут. **Выход:** текст, язык, сегменты с таймкодами,
результат M1 по расшифровке.

**Критерии приёмки:** WER <= 0.20 на записях нормального качества;
**совпадение вердикта M1 по расшифровке с вердиктом по эталонному тексту
>= 0.90** — ошибки распознавания не должны менять решение модерации;
RTF <= 0.5.

**Метрики.** ML: WER, CER, сквозная согласованность вердиктов.
Инфраструктурные: RTF, время загрузки модели, RSS, сравнение размеров модели.

**Данные для оценки.** 15 фраз на языке объявлений с заранее известным эталонным
текстом, озвученные синтезатором речи, плюс версии с наложенным шумом двух
уровней — всего 45 записей. Синтезированная речь чище живой, поэтому WER
на таком наборе — оптимистичная оценка.

### M4. Видео

**Вход:** видеофайл до 60 секунд + заявленная категория. **Выход:** найденные
объекты, флаг присутствия заявленного, число проанализированных кадров.

**Критерии приёмки:** accuracy определения присутствия >= 0.85; обработка
30-секундного ролика не дольше 30 секунд.

**Метрики.** ML: accuracy по роликам, precision/recall присутствия объекта.
Продуктовые: **зависимость качества и времени от шага между анализируемыми
кадрами** — обоснование выбранного компромисса. Инфраструктурные: время
обработки на GPU против CPU, сравнение двух размеров детектора.

**Данные для оценки.** 12 коротких роликов с известным содержимым, на каждый
две проверки — с верной категорией и с подменённой.

### M5. LLM

**Вход:** агрегированный JSON с результатами M1-M4. **Выход:** вердикт,
объяснение для продавца на русском, сводка для модератора.

**Принципиальное ограничение.** LLM не анализирует контент заново и не принимает
решение. Вердикт вычисляет детерминированное правило; модель выполняет
агрегацию по заданным правилам и генерацию текста. Такое разделение снижает риск
галлюцинаций и делает поведение воспроизводимым.

**Критерии приёмки:** модель разворачивается локально; доля валидного JSON
с первой попытки >= 0.95; совпадение вердикта с эталоном >= 0.90; скорость
генерации >= 15 токенов/с; память <= 12 ГБ.

**Метрики.** Качество: доля валидного JSON, совпадение вердиктов, сравнение
моделей разного размера. Продуктовые: время ответа. Инфраструктурные:
токенов/с на генерации и на промпте, память, размер на диске.

**Данные для оценки.** Синтетические кейсы, построенные перебором сочетаний
решений модулей M1-M4. Эталонный вердикт вычисляется тем же правилом, что
и в проде, — руками не проставляется. Каждый набор прогоняется несколько раз:
при ненулевой температуре единичный прогон не отличает устойчивую ошибку
от случайной.

## Общие требования

- Python 3.12, изолированное окружение, версии зафиксированы.
- Каждый модуль: инференс + оценка + README.
- Все замеры сохраняются в `report/metrics/*.json`; отчёт собирается из них,
  а не переписывается руками.
- Единый модуль `common/bench.py` для замеров — чтобы метрики разных модулей
  были сопоставимы.
- Веса моделей и датасеты в репозиторий не коммитятся, скачиваются скриптами.
